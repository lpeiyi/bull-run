# 需求：锁定依赖版本

> 对应 ROADMAP 第 4 项「锁定依赖版本」。

## 1. 背景与问题

### 1.1 现状

`requirements.txt` 原为**下限约束**：

```
requests>=2.28
flask>=2.2
numpy>=1.24
pandas>=1.5
```

由此带来三个具体风险：

1. **上游大版本变更可能直接导致启动失败**。`flask 2 → 3`、`numpy 1 → 2`、`pandas 2 → 3`
   都属破坏性变更，`>=` 约束下 pip 会拉到新版，而代码未必兼容。
2. **无法复现"上次能跑"的环境**。同一份代码在不同时间 `pip install` 会得到不同版本，
   出问题时无法判断是「代码改了」还是「依赖漂移了」。
3. **前后端行为可能悄悄变化**。例如 `pandas` 的 `to_csv` / `resample` 默认值、
   `flask` 的 JSON 序列化行为都随大版本调整过。

### 1.2 关键：pin 不能只改 `requirements.txt` 了事

`start.bat` 原逻辑是**每次启动都强制安装**：

```bat
"%PY%" -m pip install -r requirements.txt --disable-pip-version-check --quiet
```

在 `>=` 时代这样写没问题（约束已被满足时 pip 判定"无需操作"，秒退）。
**一旦改为 `==`，语义发生反转**：

| 场景 | `>=` 时代 | `==` 时代（若 start.bat 不改） |
|---|---|---|
| 本机版本与 pin 一致 | pip 判定已满足，秒退 | 同左，无异常 |
| 本机版本**高于** pin（曾手动升级过） | 满足约束，不动 | pip **联网降级**到 pin 版本 |
| 断网启动且版本不一致 | 已满足，秒退、不联网 | 尝试联网失败 → `exit /b 1` → **起不来** |
| 首次在新机器上启动 | 需联网安装 | 需联网安装（正常） |

也就是说：**pin 之后，"每次启动都必须联网校验"成了新的失败点**，
可靠性反而比改之前更差。因此 pin 必须与「**先探测、缺了才装**」的启动逻辑配套落地。

### 1.3 附带问题：缺少可重复的核查手段

改完文件后，没有任何办法确认"文件里锁的版本"与"本机装的版本"是否一致。
容易出现「文件改了但环境没变」的假安全 —— 这是本项目已多次踩过的同一类坑
（`market.py` 缺 `import math`、`tdx.py` 属性下标解析、`screener.py` 清单静默残缺，
共同点都是**失败被吞掉、错误不可见**）。

## 2. 范围

### 2.1 本次要做

1. **运行依赖精确锁定**（对应 §1.1）。
2. **开发依赖与运行依赖分离**，避免把 pytest 装到生产环境。
3. **提供可重复执行的依赖核查手段**（对应 §1.3）。
4. **启动链路改为「先探测、缺了才装」**（对应 §1.2）。
5. **为上述加回归用例**，尤其要有一道闸拦住"有人把 `==` 改回 `>=`"。

### 2.2 本次不做

- 不引入 `pip-tools` / `uv` / `poetry` 等依赖管理工具（本机只有裸 pip，引入新工具
  本身就是一项新的失败点）。
- **不锁定传递依赖**（不生成 `pip freeze` 全量锁），理由见 design.md §3.2。
- 不锁定 Python 解释器版本（`start.bat` 仍指向本机 3.12.10）。
- 不改动任何业务代码（`core/` 零改动）。

## 3. 用户故事

- **US-1**：作为运维者，我希望"上次能跑"的环境能被精确复现，而不是过几天因上游发版而启动失败。
- **US-2**：作为使用者，我希望双击 `start.bat` 时 —— 依赖齐备就秒起（哪怕断网），只有真缺包时才联网安装。
- **US-3**：作为维护者，我希望一条命令就能知道"文件里锁的版本"与"本机装的版本"是否一致。
- **US-4**：作为后续改动者，我希望有人把 `==` 改回 `>=` 时，立刻有一道闸拦住。

## 4. 验收标准（EARS）

### 4.1 依赖锁定（US-1）

- **AC-1.1** the `requirements.txt` shall 全部为 `<包>==<版本>` 精确锁定形式，不得含 `>=` / `~=` / 裸包名。
- **AC-1.2** the 被锁定的版本 shall 为本机实测通过全套 `pytest` 的版本。
- **AC-1.3** the `requirements-dev.txt` shall 通过 `-r requirements.txt` 继承运行依赖，并额外精确锁定测试框架。
- **AC-1.4** While 本机使用锁定版本，`pip check` shall 报告无依赖冲突。

### 4.2 核查工具（US-3）

- **AC-2.1** When 执行 `python scripts/check_deps.py`，the 核查 shall 逐包报告「包名 / 期望版本 / 实装版本 / 状态」，状态取值 ∈ {OK, 缺失, 版本不符}；任一项不满足时退出码为 1。
- **AC-2.2** When 执行 `python scripts/check_deps.py --missing`，the 核查 shall **仅依据「包是否已安装」**判定，不因版本不符而返回失败。
- **AC-2.3** When 依赖文件中存在非精确锁定行（如 `requests>=2.28`、`flask`），the 核查 shall 将其单独列出并提示"未纳入核查"，不得静默忽略。
- **AC-2.4** When 依赖文件解析结果中**不含任何**精确锁定行，the 核查 shall 判定为失败（退出码 1）。
- **AC-2.5** the 核查 shall 不发起任何网络请求，仅读取本机已安装包的元数据。

### 4.3 启动链路（US-2）

- **AC-3.1** When `start.bat` 启动，the 脚本 shall 先执行 `scripts\check_deps.py --missing` 探测依赖。
- **AC-3.2** When 探测结果显示依赖齐备，the 脚本 shall **跳过安装**直接进入启动流程。
- **AC-3.3** When 探测结果显示有包缺失，the 脚本 shall 执行 `pip install -r requirements.txt`；失败时提示原因并以非零码退出。
- **AC-3.4** the `start.bat` shall 保持纯 ASCII 编码且不含 BOM。
- **AC-3.5** the `start.bat` 中引用的脚本与依赖文件 shall 在仓库中真实存在。

### 4.4 回归与守门（US-4）

- **AC-4.1** While 改动前 **252** 个回归用例存在，本次改动 shall 不使其中任何一个失败。
- **AC-4.2** When `requirements.txt` 中任一行被改回非精确锁定，the 守门用例 `test_project_requirements_fully_pinned` shall 失败。
- **AC-4.3** When `start.bat` 的「先探测」逻辑被移除，the 用例 `test_start_bat_checks_before_installing` shall 失败。
- **AC-4.4** When 执行 `pytest`，the 全套 shall 在**离线**状态下通过（沿用 `tests/conftest.py` 的 socket 阻断夹具）。

## 5. 约束

- **C-1 不引入新依赖**：`scripts/check_deps.py` 只使用标准库（`argparse` / `importlib.metadata` / `re` / `os` / `sys`）。
- **C-2 业务代码零改动**：`core/`、`app.py`、`templates/`、`static/` 均不动。
- **C-3 环境一致**：运行与测试统一使用系统 Python 3.12.10（与 `start.bat` 同解释器）。
- **C-4 启动脚本编码**：`start.bat` 保持纯 ASCII、无 BOM，注释用英文 —— cmd 默认按 GBK 代码页解析，
  写入中文注释会被解成乱码并被当作命令执行，表现为"系统找不到指定的路径"。
- **C-5 pin 的改动纪律**：任何 pin 值变更须先在本机把 `pytest` 跑绿，再更新文件。

## 6. 非目标

- 不做传递依赖锁定（见 design.md §3.2 的取舍说明）。
- 不锁定 Python 解释器版本。
- 不引入 CI 流水线（项目无 CI 环境，且 GitHub 连通性本就不稳定）。
- 不改造 `scripts/` 下其他脚本的依赖声明方式。

## 7. 待确认事项（均已采纳推荐值）

1. **锁定粒度** —— 建议只锁**直接运行依赖（4 项）**，不生成全量 `pip freeze`。
   理由见 design.md §3.2：全量锁会把 Windows 平台专属包与间接依赖一并固化，换机器反而更易装不上。
2. **`--missing` 是否把"版本不符"也算失败** —— 建议**不算**。若算，则本机版本一旦高于 pin，
   每次启动都要联网降级，断网即起不来 —— 这恰好是 AC-3.2 要避免的。
3. **启动脚本是否保留 `pip install` 分支** —— 建议**保留**（新机器首次仍需安装），
   但只由探测结果触发，不再无条件执行。

## 8. 验收边界（诚实说明）

ROADMAP 第 4 项原验收写的是「**在一台干净机器上按锁定的版本能一次装好并启动**」。
**本次未能在真实的第二台干净环境完成该验证**（手边无可用干净机器）。

已完成的是若干**等价性较弱**的替代验证：

| 替代验证 | 结果 |
|---|---|
| `pip check` | `No broken requirements found.` |
| `scripts/check_deps.py` 逐项比对 | 4 项全 OK，实装版本与 pin **完全一致** |
| pin 值来源 | 取自本机已跑通 267 个用例的解释器环境 |
| `check_deps.py --missing` 退出码 | 0（依赖齐备，启动不会触发安装） |

**残留风险**：若目标机器的 Python 版本与 3.12.10 差异较大（例如 3.14），
个别 pin 可能不存在对应的 wheel。处置方案见 design.md §6。
