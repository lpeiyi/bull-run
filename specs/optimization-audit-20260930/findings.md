> 测试时点：**2026-09-30（周三）09:02 ~ 09:20，A 股开盘前**

## 0. 为什么选这个时点

开盘前是一天里最容易被忽略的一段：服务往往在开机时自启、用户习惯早上先看一眼。
**如果这段路走歪了，歪的是整个交易日的数据。** 实测确实在这里撞到了最重要的一个问题（P0-1）。

## 2. P0-1：清单缓存把盘前废数据锁了一整天

### 现象

`/api/market_distribution` 在 09:10 返回：

```
≥7%  19 | 5~7%  25 | 2~5% 174 | 0~2% 608 | 平盘 4265 | -2~0% 392 | -5~-2% 68 | -7~-5% 8 | ≤-7% 12
涨停 14   跌停 7   上涨 826   下跌 480   合计 5571
```

**平盘 4265 家（76.5%）** 这个数字本身就说明数据有问题。

### 根因

`core/screener.py` 第 126-135 行：

```python
fresh = now - meta.get("ts", 0) < 24 * 3600
if fresh and meta.get("complete") is True:
    return stocks, {...}        # 直接返回缓存
```

清单缓存 TTL 是 **24 小时**，但缓存内容里带着 `price` / `change_pct` / `turnover_pct` 这些**分钟级变化的行情字段**。

### 实测证据

| 项 | 实测值 |
|---|---|
| 缓存文件 | `data/screener/stock_list.json`（1.2 MB） |
| `ts` | `2026-09-30 09:00:07`（服务启动时写的） |
| `version` / `complete` | 2 / **True** |
| `price == 0` 的股票 | **3537 / 5571（63.5%）** |
| `change_pct != 0` 的股票 | 1306 / 5571（23.4%） |
| `load_stock_list_meta()` 耗时 | **0.017s** → 确认走缓存、未重拉 |

盘前集合竞价（09:15）尚未开始，**大部分股票的快照根本没更新**（`price=0`），只有少数股票还残留着上一交易日的涨跌幅。

### 影响链

```
盘前（或收盘后）打开一次页面
        ↓
拉到「63.5% 价格为空」的中间态快照 → 写缓存 complete=True
        ↓
开盘后全天，load_stock_list() 判定「24h 内 + 完整」→ 一直返回这份废数据
        ↓
涨跌幅分布图整个交易日都是错的（涨停家数严重偏低）
```

### 用户有逃生通道吗？没有

- 前端 `loadDistribution()` 调用的是 `fetch("/api/market_distribution")`——**不带 `force`**
- 「刷新数据」按钮绑定 `loadOverview(true)`，`force=1` **只作用于 `/api/overview`**
- 结果：**除非重启服务，用户没有任何办法让分布图刷新**

### 建议方向（待拍板）

> **⚠️ 已于 2026-09-30 处置，本节保留原始记录，请先读下面的更正。**
> 实施见 `specs/fix-stocklist-snapshot-freshness/`（Phase 1~4 已完成），
> 结果见 `ROADMAP.md` 第 9 项。

1. **短期**：清单缓存拆成两段——基础信息（代码/名称/行业/市值）沿用长 TTL；行情字段（price/change_pct/换手）单独短 TTL 或不缓存。
2. **中期**：`/api/market_distribution` 增加「数据是否有效」的判定，盘前/竞价前直接返回带 `stale: true` 的提示，而不是拿中间态硬算。
3. **必须配套**：前端给分布图一个能真正刷新的入口（传 `force=1`）。
4. **验收关键**：需要一个「盘前启动 → 开盘后数据自动正确」的回归用例，这是当前测试完全没覆盖的场景。

### 更正：第 1 条「拆成两段缓存」实测已否决

写这份报告时假设"全市场行情拿不到实时值"，所以拆缓存是唯一出路。**实测推翻了该前提**：

| 拉取方式 | 耗时 |
|---|---|
| 串行 56 页（改造前） | ~13.0s ← 这才是 24h 缓存真正的原因 |
| 并发 6 线程 | **4.12s**（5571 条，失败页 0） |

名单与行情来自**同一次拉取**，拆开不省任何请求。改为「拉取并发化 + 分层 TTL
（盘中 120s / 盘中外 12h）+ 有效性闸门（`price>0` ≥ 90%）」后，整体复杂度更低且达成同一目标。
原方案的另一条路（东财 `pz` / 新浪 `num` 放大条数）也已实测走不通：两者都被硬限在 100 条。

第 2、3、4 条均已按原方向实施 —— 其中第 4 条的"盘前回归用例"以**时间打桩 + 60% 空值形态桩数据**
落地（无法真机拨回 09:00），见 `tests/test_screener_snapshot.py`。

## 3. P0-2：同一屏两个「涨停」数字

| 位置 | 值 | 口径 |
|---|---|---|
| 涨跌统计柱状图最左柱 | **涨停 14** | 股票快照 `change_pct` 按分档阈值判定（bj 29.5 / 300·688 19.5 / 其余 9.8） |
| 情绪卡片 | **涨停 57** | 乐咕 / 东财涨停池（上一交易日收盘口径） |

盘前那个 14 是**快照中间态的产物**——全市场只有 23.4% 的股票有涨跌幅数据，其中 15 家 ≥9.8%（按分档阈值计 14 家）。

**两个数字都在同一页上下相邻的位置**，一个是无意义的噪声，一个是正确的昨日收盘值，页面上没有任何提示能帮用户分辨。

这条是 P0-1 的表象 + 口径混用叠加。修好 P0-1 后，两个数字至少会在同一口径下可比。

> **✅ 已处置（2026-09-30）**：修好 P0-1 后盘中复测，分布图涨停 **49~61** vs 情绪卡涨停 **41~57**，
> 从「差 4 倍」收敛到同量级。但两者口径**本来就不同**（分布柱 = 实时触板家数，
> 情绪卡 = 东财涨停池收录数），所以最终解法是**标注**而不是强行统一：
> 分布图标题标注「实时快照 + 数据时间」，情绪卡的 9 个涨停数标注「实时触板」口径。

## 4. P1-1：首屏 23.57 秒

真实浏览器实测的请求时序：

```
 0.02s   0.11s  /                          页面
 0.04s   0.09s  /static/app.js             静态资源
 0.20s  11.36s  /api/overview              ← 独占 11.4 秒，阻塞后续
11.56s   0.02s  /api/index_kline
11.56s   0.12s  /api/config
11.56s   4.78s  /api/liangneng            ┐
11.56s   0.12s  /api/market_distribution  │
11.56s   4.02s  /api/gold                 │ 8 个请求同时发出
11.56s   0.12s  /api/index_compare        │
11.56s   6.81s  /api/emotion_trend        │ ← 最慢
11.56s   0.12s  /api/emotion_low_next     ┘
11.72s   0.56s  /api/quotes
18.41s   5.16s  /api/sentiment            ← 又是 5 秒
────────────────────────────────────────
全部接口完成：23.57s
```

两个问题：

1. **`/api/overview` 独占 11.4 秒并把后续请求全部卡在它后面**（前端 `await` 完 overview 才发起第二批）。
2. **三个接口各自付一遍「情绪分 5 秒」的成本**：overview、emotion_trend、sentiment。

### 附：并发实测（澄清一个猜测）

曾怀疑 Flask 未开多线程导致串行排队。实测**推翻了**：

```
/api/overview      13.57s
/api/sentiment      4.22s
/api/emotion_trend  6.77s
墙钟 13.57s  vs  三者耗时之和 24.56s
→ 判定：多线程并发
```

但注意：**并发时 `/api/overview` 从 4.2s 涨到 13.6s**——资源竞争明显。

## 5. P1-2：情绪分是唯一的瓶颈点

在 `core/` 层逐函数计时：

| 函数 | 耗时 | 说明 |
|---|---|---|
| `emotion_history.get_emotion_trend(15)` | **0.01s** | 磁盘缓存有效 |
| `emotion_history.get_trend_view(15)` | **7.62s** | 缓存只占 0.01s，其余全是 `get_sentiment()` + 指数叠加 |
| `sentiment.get_sentiment()` | **5.38s / 5.31s** | 两次都 5 秒 |

拆开 `get_sentiment()` 的 4 次网络调用：

| # | 请求 | 耗时 | 返回 |
|---|---|---|---|
| 1 | `getTopicZTPool 20260930` | 0.86s | 0 条（盘前今天为空） |
| 2 | `getTopicZTPool 20260929` | 1.32s | 57 条 ← `_find_recent_trade_date()` 探测 |
| 3 | `getTopicZTPool 20260929` | 1.42s | 57 条 ← **参数与 #2 完全相同，纯重复** |
| 4 | `getYesterdayZTPool 20260929` | 1.42s | 33 条 |

**#2 与 #3 是同一个 endpoint + 同一个日期**：探测交易日时已经拿到了池子，主体代码又去拉了一遍。

> 对比：乐咕历史（1619 天）反而有磁盘缓存，两次调用都是 **0.00s**。缓存机制本身是好的，只是没用到最热的那条路径上。

### 建议方向

- 消除 #2/#3 重复请求（探测结果直接复用）
- 给 `_em_pool` / `_find_recent_trade_date` 加**短 TTL**（如 30~60s）——但这里有历史教训：`app.py` 的注释明确写过「sentiment 必须每次实时，避免缓存卡住旧值（如涨停83/跌停0）」。所以**必须区分「可缓存的日频数据」与「必须实时的盘中数据」**，不能一刀切。这条值得单独立 spec。

## 6. P1-3：非交易时段的「伪榜单」

### 现象

盘前打开页面，「行业领涨领跌 Top10」呈现的是：

| 领涨 TOP10 | 领跌 TOP10 |
|---|---|
| 玻璃行业 +0.00% | 玻璃行业 +0.00% |
| 基础制造 +0.00% | 基础制造 +0.00% |
| 传媒娱乐 +0.00% | 传媒娱乐 +0.00% |
| …（共 10 项） | …（**与左侧逐项相同**） |

两侧是**同一份列表**，而且「领跌」栏的数值也带着 `+` 号。

### 根因

`static/app.js` 第 632-635 行：

```js
const boards_up   = industry.slice(0, 10);                            // 原数据已按 avg_pct 降序
const boards_down = [...industry].sort((a, b) => a.avg_pct - b.avg_pct).slice(0, 10);
```

非交易时段所有板块 `avg_pct` 均为 0 → 降序与升序得到**完全相同**的结果。
代码只处理了 `industry` 为空的空态（第 626-630 行），**没处理"全部为 0"**这种情况。

### 影响

每天约 18 小时（收盘后到次日开盘）+ 整个周末，页面都在展示一份无意义的「伪榜单」；
「领跌」栏还带着 `+` 号，观感上像是在报涨幅。

### 建议方向

在 `renderBoardsTop10` 里加一个"全为 0"判定，复用既有空态文案显示
「非交易时段，暂无板块涨跌数据」。改动很小，可与 P0-1 的前端改动一并做。

## 8. 实测中被推翻的猜测（一并记录）

避免把「猜测」当成「发现」：

| 我曾怀疑 | 实测结论 |
|---|---|
| `_warmup_emotion` 预热的 `get_emotion_trend` 与路由用的 `get_trend_view` 不是一回事，预热白做 | **不成立**。`get_trend_view` 第 275 行就是调 `get_emotion_trend`，磁盘缓存实测 0.01s，预热有效 |
| Flask 未开多线程，导致慢接口串行排队 | **不成立**。墙钟 13.57s ≈ 单个最大值，确为多线程 |
| 右上角「10秒后刷新」倒计时与实际刷新间隔（60s/120s）不一致 | **不成立**。实际文案是「10秒**前**刷新」（相对时间），设计正确 |
| 页面没有标注数据日期 | **不成立**。情绪区明确标注「基于 2026-09-29 数据」 |
| 黄金卡片把「纽约黄金」错写成「纽扣黄金」 | **不成立**。`core/gold.py` 第 28 行是 `("hf_GC", "纽约黄金", "hf")`，属截图分辨率导致的误读 |

**这几处设计其实是加分的**，一并记下：休市呼吸灯、黄金折算免责声明（「非真实伦敦金数据，仅供参考」）、刷新相对时间、分布区间合计 = total（5571 精确闭合）。
