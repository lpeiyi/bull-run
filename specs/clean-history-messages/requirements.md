### 1.2 更正：ROADMAP 写「约 12 条」，实测 10 条

用 `git log --format=%B` 逐条扫描「首行是否以 `Changes to be committed:` / `On branch ` /
`Untracked files:` 等 `git status` 标记开头」得到准确值：**10 条**（上表），
不是 ROADMAP 原文的「约 12 条」。范围按实测收敛。

### 1.3 风险的本质：这 10 条在历史最底部，改它们等于改全部

这 10 条是**紧随 initial commit 之后最早的 10 条**。Git 的 commit 是链式的，
改掉第 2 条的 message 会让第 2 条及其**之后所有 49 条**的 hash 全部变化。

所以「只改 10 条 message」的实际代价是：
**本地全部 commit（核查时 51 条）都会换 hash，远端必须 `push --force`。**

### 1.4 前置条件现状（本次已逐条核实）

| 前置条件 | 核实结果 | 手段 |
|---|---|---|
| 是单人仓库 | ✅ 全部提交作者均为 `lpeiyi <lpeiyi@yeah.net>`，无第二个作者 | `git log --format='%an <%ae>' \| sort -u` |
| 没有其他人的分支 | ✅ 远端只有 `refs/heads/main`，无标签、无其他分支 | `git ls-remote origin` |
| 没有 fork | ✅ `forks_count = 0` | GitHub API |
| 本地与远端完全一致 | ✅ `db0a028` 已推送，未推送提交 **0** 条，工作区干净 | `git log origin/main..HEAD` |
| 仓库可见性 | ⚠️ **public**（非 private） | GitHub API |
| 其他机器是否有未推送改动 | ❓ **无法从本机核实，须老陆确认** | — |

倒数第二条值得单独说明：**公开仓库无法得知有多少人 clone 过**（clone 不产生 fork，也不留记录）。
不过 `forks_count = 0` 且这是一个个人自用的盯盘工具，实际被他人克隆的概率很低。

## 2. 范围

### 2.1 本次要做

1. 把 §1.1 表中 **10 条**提交的 message 改写成 `type(scope): 中文简述` 格式；
2. 每条保留原始文件清单作为 message **正文**（信息零丢失）；
3. 全流程可回滚：动手前做全量备份，备份可一键恢复；
4. 改写后 force-push 到 `origin/main`，并核实远端与本地一致。

### 2.2 本次不做

1. **不改任何提交的内容（tree / 文件 / 作者 / 时间戳）** —— 只动 message 文本；
2. **不动 `.trae/specs/` 里任何文件**（Trae 遗留目录，按项目约定保持原样）；
3. **不改其余提交的 message** —— 包括第 1 条 `initial commit: ...`（它是 Git 默认风格，
   语义清晰，行业惯例也不强求套 `type(scope):`）与第 12 条起已规范的那批；
4. 不引入新依赖到 `requirements*.txt`（重写工具的选型见 design，
   若需临时安装，只在助手沙箱内或临时使用、不写入项目依赖文件）；
5. 不改 `ROADMAP.md` 之外的项目文档内容结构（只更新第 7 项状态与其事实更正）。

## 3. 用户故事

- **US-1**：作为仓库唯一维护者，我希望 `git log --oneline` 从头到尾都能看懂每次改了什么，
  这样回溯「某段逻辑是什么时候、因为什么加进来的」时不必逐条 `git show`。
- **US-2**：作为维护者，我希望这种「整理历史」的操作是**可控且可反悔**的，
  即使中途出错也能一条命令回到动手前的状态。
- **US-3**：作为维护者，我希望改写历史**不带来任何内容层面的变化** ——
  每个 commit 里有哪些文件、文件什么内容，必须和改写前逐一相同。

## 4. 验收标准（EARS）

### 4.1 消息改写的完整性（US-1）

- **AC-1.1** the 重写流程 shall 使 §1.1 中列出的 10 条提交的 message **首行**全部匹配
  `^(feat|fix|refactor|docs|test|chore|style|perf|build|ci)(\([a-z0-9_.-]+\))?: .+`。
- **AC-1.2** the 重写流程 shall 保持其余全部提交的 message **逐字节不变**
  （含行尾空白与末尾换行）。
- **AC-1.3** When 改写某条 message，the 重写流程 shall 把该提交原有的文件清单
  原样保留在新 message 的正文中（不得只留一句概括而丢掉清单）。
- **AC-1.4** the 重写后的仓库 shall 满足 `git log --oneline` 中不存在任何以
  `Changes to be committed:`、`On branch `、`Untracked files:`、
  `Your branch is`、`nothing to commit` 开头的 subject。

### 4.2 内容零变更（US-3，本次最关键的一条）

- **AC-2.1** the 重写后的仓库 shall 满足 `git diff <旧HEAD> <新HEAD>` 输出为空。
- **AC-2.2** While 按「从最早算的序号」逐条对应新旧提交，
  the 重写后的仓库 shall 满足**每一条**提交的 `tree` 哈希与原提交逐一相同
  （条数以重写执行时的实际总数为准 —— 2026-09-28 核查时为 51 条；不是只比 HEAD）。
- **AC-2.3** While 按序号逐条对应，the 重写后的仓库 shall 满足每条提交的
  **作者、提交者、作者时间、提交者时间**均与原提交一致。
- **AC-2.4** the 重写后的仓库 shall 满足 `git status --porcelain` 输出为空（工作区干净）。
- **AC-2.5** While 在重写后的仓库上运行完整测试套件，
  the 测试 shall 全部通过（用例数与重写前一致）。

### 4.3 可回滚（US-2）

- **AC-3.1** While 重写开始之前，the 重写流程 shall 已生成一份可独立恢复的全量备份
  （`git bundle --all` 产物或等价物），且 shall 校验该备份可被 `git bundle verify` 通过。
- **AC-3.2** While 重写开始之前，the 重写流程 shall 在本仓库留下指向旧 HEAD 的
  本地引用（如 `refs/backup/pre-rewrite`），使回滚可在**一条命令**内完成。
- **AC-3.3** If 改写后任一 §4.2 条款不成立，
  the 重写流程 shall 立即回滚到备份引用，而**不得**执行 force-push。

### 4.4 前置安全（US-2）

- **AC-4.1** While §1.4 中「其他机器是否有未推送改动」这一条尚未由老陆确认，
  the 重写流程 shall 不开始执行。
- **AC-4.2** the 重写流程 shall 使用 `--force-with-lease` 而非 `--force` 推送，
  以避免覆盖掉核查之后远端新出现的提交。
- **AC-4.3** While force-push 之前，the 重写流程 shall 已记录旧 HEAD 的完整 hash
  并完成一次「旧 hash 仍可通过备份取回」的验证。

## 5. 约束

- **C-1 只动 message**：任何改写都不得触及 tree、blob 与提交元数据。这是本次唯一的不可协商项。
- **C-2 网络受限**：本机在公司内网时须经代理访问 GitHub；助手沙箱代理连不了外网，
  联网操作须出沙箱执行。推送统一走既有自适应脚本
  （`.workbuddy/skills/windows-git-push-troubleshoot/scripts/git_net.py`）。
- **C-3 工具可用性（已实测）**：`git filter-repo` **未安装**（命令与 Python 模块都没有）；
  内置 `git filter-branch` 可用（git 2.55.0），但已废弃并会打印告警。
  选型属 design 阶段决策。
- **C-4 `.trae/specs/` 保持原样**：该项目目录是 Trae 遗留，按既有约定不改动。
- **C-5 依赖文件不受污染**：若需临时安装重写工具，不得写入 `requirements*.txt`。
- **C-6 提交风格**：本条自身的产出（spec 文档 + ROADMAP 更新）按
  `docs: 中文简述` 提交，与既有规范一致。

## 6. 非目标

1. 不做「历史裁剪」类操作 —— 不删除任何提交、不合并提交、不改写目录结构；
2. 不重写已规范的 message 去"统一风格"；
3. 不为将来的提交加 hook 强制校验（ROADMAP 第 2 项已覆盖规范，本次不扩范围）；
4. 不追求让旧 hash 从 GitHub 上彻底消失 —— 公开仓库上旧对象会在一段时间内仍可通过
   已知 SHA 访问，这不是本次能承诺的目标。

## 7. 待确认事项（附推荐值）

| # | 事项 | 推荐 | 理由 |
|---|---|---|---|
| 1 | **是否真的做** | **建议做** | 前置条件已核实到位（单人 / 单分支 / 0 fork / 本地远端一致）；改动只动文本、有备份、可一键回滚；不做的代价是这 10 条永久不可读 |
| 2 | **其他机器是否有旧克隆** | 老陆确认 | 若有，该机器需删除重克隆（或 `git fetch --all && git reset --hard origin/main`）。**这是唯一未核实项**，也是本次唯一可能造成他人困扰的地方 |
| 3 | **改写粒度** | 每条 = 一句概括 + 原文件清单原文 | 满足 AC-1.3 的信息零丢失；概括内容由助手读 `git show` 后人工撰写，需老陆过目 |
| 4 | **时间戳是否保持** | **保持原样** | 只改 message 是本次的核心约束（C-1）。保持时间戳可让 AC-2.3 成为可自动校验的强断言 |
| 5 | **写一个可复跑的脚本吗** | 建议写，但放 `scripts/` 之外或标注为一次性 | 历史重写是一次性操作，脚本本身是本次的执行载体与留痕；若老陆认为该脚本有二次利用价值，再决定是否正式归档 |

## 8. 验收边界（诚实说明）

本次能保证与不能保证的事，分开说清楚：

**能保证**
- 每个 commit 的 tree 逐一相同（AC-2.2）→ 文件内容零变化是可验证的
- 10 条 message 改写到位、其余提交逐字节不变（AC-1.1 / AC-1.2）
- 完整测试套件仍全绿（AC-2.5）
- 备份存在且回滚可用（AC-3.1 / AC-3.2）

**不能保证**
- **旧 hash 从 GitHub 上消失**：公开仓库的旧对象在一段时间内仍可按已知 SHA 访问
  （GitHub 的 GC 策略不由我们控制）。若老陆在意「旧历史不可再取」，那需要的是
  删库重建，不是本条 —— 那属于另一个（更彻底的）决策。
- **其他人手上的旧克隆自动修复**：force-push 后，别人的克隆会「多出一条自己造的分叉」，
  必须手工处理。这是 AC-4.1 要求先确认的原因。
- **概括写得"对"**：10 条改写后的中文描述由助手根据 diff 撰写，属于**人工判断**产物，
  不排除对某次改动的意图判断有偏差。缓解手段是改写结果先给老陆过目再 force-push。

## 9. 与其他 ROADMAP 项的关系

- **第 2 项「提交规范化」**：已从那 10 条之后的第 12 条起生效，本条是把这项工作的
  时间边界向历史方向补齐。做完之后，ROADMAP 第 2 项的语义才真正覆盖全部历史。
- **第 6 项「app.py 路由瘦身」**：刚完成，其 7 个提交已推送（`fbdc225`…`db0a028`）。

  这一顺序安排的原因（见前一轮结论）。
- **本条完成后 ROADMAP 全部 8 项归零。**
