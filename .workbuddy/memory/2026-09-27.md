## 排障过程（根因值得记住）

### 现象
`git push` 挂在后台 **12 分 50 秒无任何输出**，进程在跑、TCP 连接 ESTABLISHED，
但就是不动。此前一轮曾误判为「企业网络拦 GitHub」。

### 逐步排除
1. 直连 `https://github.com` → HTTP 200（9.2 秒，慢但通）；gitee 也通
   → **不是网络封锁**
2. `git ls-remote origin HEAD` → 秒回
   → 但这是公开仓库，**读操作匿名即可，没验证到写入认证**
3. `push --dry-run` + `GIT_TERMINAL_PROMPT=0` → 报
   `could not read Username for 'https://github.com'`，随后挂到超时
4. 上 `GIT_TRACE=1 GIT_CURL_VERBOSE=1` 抓日志 → 看清全链路：
   - 服务器返回 `HTTP/1.1 401 Unauthorized`
   - git 调凭据助手 → **`git credential-helper-selector get` 跑了 44 秒**才返回
   - 之后才轮到 `git credential-wincred get`

### 两个根因
1. **全局凭据助手是个弹窗选择器**
   `~/.gitconfig` 里 `credential.helper = helper-selector`
   （WorkBuddy 自带 PortableGit 提供，`mingw64/bin/git-credential-helper-selector.exe`）。
   它在无 GUI 的后台被调用时会一直挂着等用户点选，这就是那 12 分钟的来源。
2. **`credential.helper` 是累加型配置，`-c` 覆盖不掉它**
   我一开始用 `-c credential.helper=wincred` 想覆盖，结果 git 仍先跑 selector
   （配置读取顺序 system → global → local → 命令行，多值键全部保留）。
   正解：先 `-c credential.helper=`（空值 = 清空列表）再追加 `-c credential.helper=wincred`。

### 附带发现（非阻断，但属错误配置）
- 全局 `~/.gitconfig`：`http.proxy = https.proxy = http://127.0.0.1:8080`
  → 本机 8080 端口**并无服务**（实测 /dev/tcp 探测 closed）。
  系统真正的代理是企业内网代理 `proxy.xn.petrochina:8080`，但它拒绝访问
  GitHub（返回 503）。**直连反而是通的。**
- 全局 `http.sslverify = false`（降级配置，建议知会老陆评估）

## 修复动作（只动本仓库，未改全局）

→ **用户以为在全市场选股，实际漏掉 94.6% 的标的，界面无任何提示**。

**关键判断（值得记）：旧格式缓存不享受 24h 直用**
设计原表写「未过期且结构合法 → 直接用」，但旧文件无 `complete` 字段。
若照原表直用，那份 300 条残缺缓存还能再活 24 小时。故改为：
**只有 `complete is True` 的缓存才走 24h 快路径**；无 `complete` 的一律视为「可能不完整」，
先尝试重拉，成功即写为 v2、失败才降级回退。这样老陆那份残缺清单在首次成功拉取时被自动修正。

### 教训 / 复用手法
- **`_sina_get` 是唯一网络出入口**，把它替换成内存假接口即可让整个分页逻辑脱网可测；
  假接口除返回分页数据外**记录请求过的页序列**，才能断言「失败后仍继续拉后续页」这类行为
- 测试里必须同时把 `screener.time.sleep` 置空，否则单页重试要真等 4.5s
- 幂等的「体检/清理」类脚本，把纯函数（`collect_kline_files` / `plan_clean` / `apply_clean`）
  与命令行壳（`cmd_report` / `cmd_clean`）分开，前者可被 tmp_path 直接测，
  后者只需把 `load_manifest` 打成桩即可测「降级拒绝清理」
